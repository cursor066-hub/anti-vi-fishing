# Operator runbooks

These are actionable local engineering procedures and proposed production response sequences. No organisational on-call assignment, SLA, external incident exercise or production DR has been validated. Security, platform, finance/data owners and customer custodians must be formally assigned before production acceptance.

## Certificate rejection

Use the machine-readable error and request ID; do not log the request body or token. For `INV-409-STATE`, compare the current target state, active policy version and evidence graph to the exact signed capsule. Cancel undispatched authority and create a separately reviewed new capsule if the business request remains valid. Do not edit a certified capsule or re-use its nonce. For expiry, re-propose and obtain fresh evidence/approval. For replay, inspect the existing certificate outcome; a replay error is not a request to mint a duplicate payment.

## Target uncertainty

An operator uses `GET /gate/v1/outcomes/{certificate_id}` or Reconcile target outcome. VERIFIED is valid only after observed target journal state matches the authorised fields. If no authoritative outcome exists, the result remains UNCERTAIN. Stop replacements for the same business transaction and have the real target owner establish execution/non-execution through an authoritative reconciliation channel. Never infer success or failure from a timeout. The simulation has no manual “mark successful” override and no blind retry button.

## Gate/process outage and restart

Preserve the deployment directory, private configuration and both SQLite databases. Stop the service gracefully (`SIGTERM`) rather than deleting state. Restart the same reviewed code with the same directory and configuration. A consumed reservation remains consumed after restart. Reconcile any EXECUTING/UNCERTAIN records. The included restart test demonstrates reservation persistence, not a production RTO or multi-zone failover.

For an actual database backup, use the shipped tooling: `node scripts/backup.mjs --dir <deployment> --out <backup-dir>` performs an engine-native online backup (WAL checkpoint + `node:sqlite` backup API, consistent snapshot — never a raw `.db` copy) and writes a signed-content manifest (`IF-BACKUP-1` with SHA-256 per file). `node scripts/restore-check.mjs --dir <backup-dir> --trusted-keys <deployment>/config.json` verifies the manifest offline under an external trust anchor (the keys embedded in the artifact are informational only): hashes match, schema versions are readable, the audit chain re-verifies entry-by-entry and its per-tenant head/length matches the signed commitment, and cross-database references are consistent. The drill is exercised in CI via `scripts/simulate.mjs`. Key material outside the databases (vault file, master key, config) must be backed up separately under custodian control. Retain original checkpoints and encrypt backups under separately controlled keys. Production backup scheduling and remote key escrow are not implemented.

## Key or issuer compromise

The security role invokes `POST /v1/revocations` with the affected key/issuer/subject/certificate, an incident reason, and a separately authenticated token. This blocks future local use and preserves evidence. If the execution/audit-key host is compromised, isolate it first; application-level revocation cannot make a malicious host trustworthy. Preserve external checkpoints and forensic copies.

Rotation procedure: (1) `POST /v1/keys/rotate-prepare` with the affected `key_class` — the vault generates a **pending** key that cannot sign anything; (2) propose a `key.rotate` action binding `new_key_id`, the pending key's `new_public_key`, a `ceremony_id` and `revoke_old`; (3) collect `governance_review` evidence from two independent failure domains; (4) collect three custodian approvals and honour the cooldown; (5) certify and execute — the pending key activates and the old key is retired. `GET /v1/keys/{id}/attest` produces a signed software attestation for the new key. Unilateral rotation does not exist: the action is the authority.

Secret recovery procedure: `POST /v1/ceremonies` creates a k-of-n ceremony with named custodians and a validity window. Each custodian acknowledges with an offline envelope signed with purpose `ceremony-acknowledgement` (e.g. `node src/cli.mjs sign --purpose ceremony-acknowledgement ...`, then `POST .../acknowledge`). Only then may `POST .../split` divide a base64url secret into committed shares for distribution. `POST .../reconstruct` requires k distinct shares; a duplicate or below-quorum set is refused. The service never retains the secret.

## Suspected tenant isolation incident

Stop affected ingress, preserve encrypted state and minimal request-ID logs, record UTC times and affected component versions, and engage the assigned incident lead and privacy/legal owner. Keep tenant payloads compartmentalized. Revoke compromised principals and credentials under the approved customer process. Reproduce the suspected boundary failure only against isolated synthetic data. Document containment, scope, impact, recovery, root cause and corrective actions. Notification obligations require legal review, not a blanket product claim.

## Policy defect

Cancel unexecuted affected actions and revoke pending certificates. Use the exact policy simulator to review a correction. Root activation requires sequential policy version, reviewed exact diff, required evidence, delay and customer quorum. Never clear the revocation store or rewrite audit history to roll back a policy. Code rollback and authority rollback are distinct operations.

## Clock, evidence and hardware failures

A detected backward clock movement stops security mutations with `INV-503-TIME`. Restore an authoritative clock under operator control and preserve evidence; do not change stored last-seen time to bypass the check. Missing, expired or dependent evidence remains escrow. Synthetic health expires after 24 hours. Real attestation and protected recovery are unavailable; there is no universal refresh override. Secure Perception in this release is the dev-attested software profile — hardware attestation still fails closed.

## Evidence issuer operations

Start issuers with `node src/cli.mjs issuerd --dir <deploy>/issuers [--port 8090]` or `node src/issuerd.mjs --dir ... --port ...`. Each `*.issuer.json` spec carries its own key, channel, record store and optional `tenant` scope; two tenants may run same-named issuers — the registry keys are `<tenant>:<issuer>` and bare-name requests are refused when ambiguous (`?tenant=` on manifest/health, `tenant_id` in the issue body). The issuance log is appended per query at `<dir>/issuance-log.jsonl`. `POST /v1/connectors/{key_id}/drift-check` compares registered trust metadata with the live signed manifest and audits `CONNECTOR_DRIFT`; investigate version, kinds, channel or key changes as a potential connector compromise. Updating an issuer spec requires the same governance as any trust-registry change; do not edit spec files on a running daemon without a witnessed procedure.

## Audit chain seal (tail remediation)

Every read of the audit index re-verifies signatures, digests and chain links; an unverifiable row wedges the index deliberately (`INV-409-INTEGRITY` / `INV-409-AUDIT-TAMPER`) — a fail-loud state, not a corruption to bypass. Two remediations:

1. **Poisoned tail** (corruption begins at the newest rows, e.g. a row appended outside the signer): `POST /v1/audit/seal` as a `security` role. The call scans the chain to the first unverifiable row, then inside one transaction drops the audit triggers, deletes every doomed row (stored seq at or after it, plus verified-doomed rows rewritten below the cut), recreates the triggers and lands a signed `AUDIT_SEALED` event (with `sealed_at_seq`, `removed_count`, removed head/tail digests, and `*_carryover` re-attesting the cut span's verifiable spend/access/capability/revocation state plus `lifecycle_carryover` for every other verifiable doomed event — spent stays spent, cancelled stays dead, composite children stay bound — while rows it could not re-verify are named under `dropped_events` and force worst-case reconstruction budgeting; overflow is paged onto signed `AUDIT_SEAL_CARRY` rows chained by `seal_seq`; mirror-table residue it declined to carry is named under `dropped_mirrors`). Authorization is break-glass — checked against the frozen tenant identity set because the chain itself is unavailable — and is recorded on the chain. Doom follows each row's *signed payload sequence*, so stored-column surgery on a doomed row is carried by payload truth and counted under `carryover_totals.divergent_stored`; deleted payload positions are attested under `deleted_gaps`; orphaned revocation floor rows carry as `floor_derived` (enforced, named in the result, never gating the sealer); a floor row whose content contradicts a verifiable `record_digest` anchor is convicted under `planted_floor_refs`; a floor row DELETED while an anchor still condemns the ref is named under `murdered_floor_refs` — still enforced, listed by the revocations query as `anchorless-carried`, and re-anchorable via a fresh signed revocation (`POST /v1/revocations`); carry pages bind the seal's assigned `seal_seq` (returned in the result), not the nominal cut point, and an amputated `AUDIT_SEAL_CARRY` page refuses `INV-409-INTEGRITY` on every later call — restore the page before resuming; a killed audit signer fails `INV-503-CONFIG` with the blocking key refs named in the message (when the dead key has a chain-attested successor the seal repoints to it — a carried `key:` revocation or `KEY_ROTATED` inside `lifecycle_carryover` counts as the death event — and the successor must be ceremony-designated). A caller whose own `AUTHORITY_REVOKED` is anchored (verifiably carried — a floor-derived claim alone never blocks them) is refused `INV-403-QUARANTINE`. On a *verifying* chain the call is not inert: it can land `AUDIT_HEAD_REANCHORED`, lower a stranded durable watermark to the verified tip, disclose anchorless floor rows under `floor_divergent`, attest a deleted-tail regression as `head_regressed: true` + `abandoned_head_seq/hash` (or refuse `INV-409-INTEGRITY` when the surviving head's floor/checkpoint claims regress), or write `AUDIT_WEDGE_CLEARED` after the integrity sweep passes — those return `sealed: false` but still mutate the signed ledger. A wedge-clear result also carries `unverifiable_cleared: true` and `resurrected_total`, and the `AUDIT_WEDGE_CLEARED` event names each resurrected anchored authority under `metadata.resurrected` (bounded to 512 entries) — rows (e.g. still-valid JIT grants) that the rewound/repaired horizon would have resurrected; each entry is `{kind, id}` so the responder can re-quarantine them deliberately rather than letting them silently ride the repair (w45-runtime F1). Investigate the cause before resuming traffic; the seal preserves evidence of *that* rows were removed and re-attests what it could prove of their contents.
2. **Mid-chain corruption** (any rewritten row below the tail): the seal path cannot repair it — every option would silently falsify history. Restore from the last good backup and run `node scripts/restore-check.mjs`, then re-attest. Treat any seal event or restore as a reportable integrity incident.

**Head-file loss or a poisoned signed head.** `chain-heads.json` deleted or replaced over committed rows reads `corrupt` — the seal paths then attest `prior_head_unverifiable: true` inside the `AUDIT_HEAD_REANCHORED`/`AUDIT_SEALED` record and result instead of reporting a clean repair (the wiped floor/checkpoint claims are destroyed evidence, named not refused — refusing would let the file wipe permanently disable remediation). A head whose signed `checkpoint`/`checkpoints`/`revocations` claims can never be re-proven (planted residue claimed by a pre-w38 head) wedges every fold `INV-409-INTEGRITY` and `store.audit` with it — heads minted since w38 only claim *verified* residue, so a new mint cannot be poisoned. To recover a pre-w38 poisoned head in order: delete the planted `records` rows → delete `chain-heads.json` and `head-watermark.json` → `POST /v1/audit/seal` — the verifying chain re-anchors the tip under a fresh head and names the destroyed attestation on the signed record.

**Tampered durable watermark.** `head-watermark.json` entries are signed headmark envelopes once a signer exists — a bare number is the legitimate pre-signer/refusal fallback, never a forged-high floor: unsigned claims above the verified tip never wedge, folds clamp to the verified tip and surface the entry as `head_watermark_tampered` (`{tenant_id, kind, seq}`) in error details and on `POST /v1/audit/seal` results (`kind` distinguishes `unsigned_above_head` / `unsigned_downgrade` / `signature` / `malformed` / `dead_signer` / `sign_failed` / `planted_content` / `floor_stripped` / `write_failed` / `floor_marker_ahead` / `floor_marker_forged` / `floor_marker_malformed` / `floor_marker_orphaned` / `floor_marker_healed` / `facts_regressed`). A *signed* stranded floor still wedges honestly — the seal lowers it to the verified tip and writes `AUDIT_WM_REANCHORED` naming `reanchored_tip_seq`, `abandoned_watermark_seq` and `abandoned_watermark_signed`. Any `head_watermark_tampered` sighting is an integrity incident: it means a writer to the watermark file tried to pin a head the chain cannot prove — diff the file against the last known-good head before resuming. Residual bound: the read-then-write on the file is not atomic — a writer landing a fresh entry between the read and a sanctioned rewrite can leave a torn floor. The file is re-read on every open and every fold, so the next surface converges and attests the same divergence; the window is bounded to one surface, not permanent. Likewise, POSIX mode bits on the ledger files bound only a non-owner attacker — a writer with the owner's credentials bypasses every mode check by definition; detection above the file layer (markers, signed heads, anchors) is the residual control, not the mode bits.

**`floor_marker_ahead` — head-pair rollback or lost flush.** Every audit append also lands an in-ledger `meta_kv.fold_floor` marker `{seq}:{tip_hash}` in the same transaction — it is not part of the replayable file pair, so it survives a coherent `chain-heads.json` + `head-watermark.json` rollback. When the fold sees the marker ahead of *every* witness that could attest its span — the committed rows AND the signed head — it attests `floor_marker_ahead` (a mid-cut seal and a pure crash gap no longer self-report: the surviving head/rows still cover the marked seq): the evidence distinguishes two shapes it cannot tell apart internally — (a) a crash between commit and head-file flush (legitimate, bounded to the last commit's lag), and (b) an attacker restoring an older signed pair after deleting the matching tail rows (a coherent rollback erases events silently on fresh open). Any sighting on a deployment that did NOT just crash mid-write is an integrity incident: expect rollback surgery, compare the marker's `{seq}:{tip_hash}` to the files' claimed head (the hash half is verified against the chain row at that seq — a mismatch is `floor_marker_forged`, a transplanted or hand-written marker; a value that is not `seq:hash` at all is `floor_marker_malformed` — no honest write produces that shape; a marker inside the surviving committed span whose row is gone is `floor_marker_orphaned` — a surgical in-span hole no seal cut or retirement can leave), and reconcile what the deleted tail contained. `floor_marker_malformed`/`orphaned` never self-clear and are never retired by a subsequent clean read — they are latched until a report surface attests them (a refusal is *not* an attestation surface — an attacker-inducible refusal can never retire a conviction; only a delivered report or the sanctioned re-anchor that mints `AUDIT_WM_REANCHORED`/`AUDIT_HEAD_REANCHORED` can). The append path heals a malformed marker it cannot honor (a CAST-high plant would otherwise wedge every append, including the seal's own mints): the divergent content moves to `meta_kv.fold_floor_healed.<seq>` keyed to the healing append — evidence, never silent erasure — and surfaces once as `floor_marker_healed` on the next fold report. The same heal covers a well-formed-*shaped* plant ahead of the committed tip (`99999999:planted`): it passes the `/^\d+:/` shape check yet can never be an honest write — the guarded UPSERT refuses it and every later epoch attestation would wedge forever — so the append overwrites it with the true tip and attests the divergence on its own signed envelope as `fold_floor_divergent` plus the keyed residue row (w66-seal F-2). A seal cut deletes the marker with the doomed rows it named (it would otherwise convict phantom `floor_marker_ahead`/`forged` on every later seal); the empty-chain re-anchor arm consults the marker before deleting it. Residual bound: a rollback that *also* rewrites the marker row is outside the file+DB threat bound — the marker adds a required-alignment layer, it does not make rollback impossible.

**Residue heal + retirement plane.** Consumption of healed residue is triple-bound: signed `FOLD_RESIDUE_RETIRED` mints (paged at 512 claims per row, carrying `retired_page`/`retired_pages`/`retired_total`), `retired_claims_fold` inside the `AUDIT_SEALED` envelope, and `meta_kv.fold_floor_retired` — a signed `{claims, env}` marker verified under the audit key set on every consult. The marker keys are guarded by the `fold_residue_keep`/`fold_residue_keep_upd`/`fold_residue_keep_ins` triggers (delete/update/insert on residue or marker keys aborts 'fold-floor residue is evidence'); every sanctioned recreate draws the same canonical text from `RESIDUE_KEEP_TRIGGERS` in `src/store.mjs`. Before the guards drop for a retire, the in-flight claim set is signed into the marker itself as `fold_floor_retiring` (envelope `{tenant_id, fold_floor_retired: prior, fold_floor_retiring: mintable, marker_seq: committedTip, marker_tip_hash: recomputed tip hash}` inside a `residue_note` savepoint — the sign runs *before* the trigger drop, and a corrupt standing marker is never overwritten by the note) so a crash between mint-commit and drain re-derives the window durably rather than as tamper evidence; the drain's marker rewrite clears it. Since w65 every marker envelope — retire mints and retiring notes alike — pins `marker_tip_hash`, the recomputed `hashBytes` of the `marker_seq` row's envelope bytes: a pre-w65 envelope without the field never authenticates, and a stored-hash-column rewrite fails the pin (the tip is recomputed, never read from the column), so both land `floor_marker_retired_forged` rather than authenticating a grafted or replayed marker (w66-seal F-1). Claim filtering before signing: a value with no `seq:` head or an empty marker convicts `floor_marker_retired_unshaped` and is drained unsigned; a claim whose seq outruns the committed chain tip convicts `floor_marker_residue_premature` and is drained unsigned; the 4096 bound caps the marker's `retired` *field* only (the merge slices `prior` to the write contract with fresh claims heading) — `FOLD_RESIDUE_RETIRED` mints are unbounded, so a full marker never starves the consumption mints (w64-seal F-4); a claim whose seq is not a safe integer convicts `floor_marker_residue_premature` identically to one past the committed tip (w64-seal F-3). Marker envelopes are minted only under a signer live at `marker_seq` — a configured key dead in the fold (rotation or revocation) steers the write to the live successor instead of signing an envelope every consult would refuse (w64-seal F-1). On the read side, a marker's `retiring` AND `retired` sets are honored only while `marker_seq` sits within 8192 seq of the cursor's scan tip — an older envelope reads as replay/graft and cannot mute `floor_marker_residue_retired_echo` (w64-seal F-2); the window is honored only while the scan cursor is itself proven — every freshness predicate requires a positive cursor (`tip > 0`/`scan.seq > 0`), so a cursor stuck at 0 under an unstable shape probe never vouches a stale marker fresh (w70-fv F-1); a claim anchored above its own `marker_seq` refuses the envelope outright, so a backdated env cannot suppress a heal it could never have seen. Claim-keyed flags carry a bounded `claims[]` sample of the rejected values (last 16 distinct) and `claims_dropped` admits how many fell off the tail (w64-runtime F-1). Flag semantics on report surfaces: `floor_marker_residue_retired_echo` — a residue row still standing after its claim was retired (defeated drain or replant); `floor_marker_residue_capped` — residue enumeration hit its cap; `floor_marker_residue_premature` — a claim naming a seq beyond the committed tip (a heal that never anchored); `floor_marker_healed_unanchored` — a heal pointer naming no verifiable anchor row; `floor_marker_retired_unauthenticated` — a marker that parses but carries no verifiable signature envelope; `floor_marker_retired_forged` — a signature or claims verification failure on the marker; `floor_marker_retired_malformed` — non-JSON marker content; `floor_marker_retired_unshaped` — a residue value that fails the `seq:marker` claim shape; `floor_marker_retired_overcovered` — a durable marker claiming retirements the standing residue rows do not cover (claims outliving their evidence); `floor_marker_retired_marker_defeated` — a marker write or residue delete refused while `meta_kv` stood, carrying the bounded `claims[]` sample of the set the write meant to record (a defeat inside an aborted transaction re-latches as a flag on the error path — the marker the probe saw standing survives the rollback, so the rolled-back conviction reaches the next report rather than dying with the tx); `floor_marker_retired_deferred_dropped` — a drain-deferred claim set whose apply met a standing marker that could not authenticate: the queueing gate suppresses only the mint, never the drop, so the refused set is named here with a bounded `claims[]`/`claims_dropped` sample instead of evaporating silently; `floor_marker_retired_murdered` — a standing marker that could not authenticate (forged, malformed, or unauthenticated): the keep triggers once made it undeletable and the mint gate refused to overwrite it, so one planted row wedged the whole suppression plane — the drain now deletes it inside its guarded span (guards already down, landed-delete probed) and names the kill post-commit so a rollback cannot claim a delete that never happened; `floor_marker_retired_evicted` — a marker envelope whose signed `prior_evicted` is positive: claims pushed off the 4096-claim union cap before the write, so the marker itself attests how many convictions it no longer names (`floor_marker_retired_malformed` never self-clears without an attestation surface). `prior_evicted` counts eviction *events* across marker rewrites — a claim re-anchored and evicted again counts twice — so the signed number is a monotone upper bound on distinct displaced claims, never a shrink (w69-seal NIT); it now also includes the fresh-side pre-cap slice the write dropped, so the counter can no longer under-report its own class (w69-runtime F-7). For that count to be honest on the deferred path the queue carries the UNCAPPED union of drain claims — a capped queue could never report a pre-cap drop it never saw (same finding). The counter honors the same 8192-seq freshness window as the claims it accounts for — a stale envelope's `prior_evicted` is replay, not fresh accounting, and is zeroed on the drain, `residue_note`, deferred-apply, and consult-latch reads alike (w70-runtime F-2). The drain-deferred queue is in-memory by design: a crash between seal commit and apply loses the `fold_floor_retired` bookkeeping row, while the claims' own `FOLD_RESIDUE_RETIRED` mints already anchor the evidence — bounded loss, replayed next seal (w69-runtime F-8); an aborted seal restores the entry snapshot unioned with anything drains queued mid-seal, so the aborted seal never drops claims the next committed seal must mint (w70-runtime F-1). The deferred queue only stages outside a transaction — `callerInTx` is snapshotted before the drain savepoint and an in-tx drain mints the envelope in place, so a rolled-back tx can never leave phantom claims (w71-runtime F-4). The apply also shares the drain's murder doctrine: a standing marker that cannot authenticate is deleted inside `SAVEPOINT deferred_mint`, probed, and named by the same defeated/murdered flags while the queued claims land under a fresh env — one corrupt row can no longer wedge every drain-less pass (w71-seal F-3); and a consult that cannot evaluate (transient storage/catalog fault, an errcode-less throw) degrades to no-consult — never a murder, never a refused-write verdict — the queue stays retained for the retry (w71-seal F-1/F-2). `_seenTotal` merges monotonically on every tamper-set path so `claims_dropped` never understates a repeated flood (w71-runtime F-1), and a raw post-commit seal fault carries `deferred_apply_error` like its typed siblings (w71-runtime F-2). The deferred apply re-reads the standing marker INSIDE `SAVEPOINT deferred_mint` — a peer write landing between the drain's commit and the apply merges into `prior` instead of being clobbered by a pre-savepoint snapshot (w70-seal F-5). Its fault classification is errcode-only — attacker-controlled `RAISE(...)` text can spell 'database is locked' but cannot mint a real BUSY, so message-text steering into the retry class is denied (w70-seal F-1/F-3): base `SQLITE_BUSY`/`SQLITE_LOCKED` (5/6) surfaces `INV-503-LEDGER` (transient — retry, the queue is retained and replays on the next seal), storage-class bases (8/10/11/13/14/15) surface `INV-503-STORAGE`, and every other errcode is a REFUSED WRITE — the `floor_marker_retired_marker_defeated` flag latches with the claim sample and the apply rethrows `INV-409-INTEGRITY` rather than leaking a raw `SqliteError` (w70-seal F-1). The apply runs inside the seal's `finally`: a fault there now rides the delivered shape as `deferred_apply_error` (the same convention as `vault_persist_error`) on the committed seal's result, or on the thrown fault's `details` for a post-commit failure — a bookkeeping fault can never report a committed seal as denied (w70-seal F-2); the seal's `_chainFacts` consult inside the apply degrades to not-fresh on a fault instead of escaping raw (w70-seal F-6). Conviction retirement is delivery-bound: repair paths (the landed re-anchor's marker delete, the residue drain) capture their flag kinds into the report and `#wmTamperReported` retires a kind only when the standing flag still serializes to exactly the rows the delivered report carries — a kind latched or mutated between collect and delivery stays live and is named by the next report, and a post-commit throw can no longer erase both the evidence row and its conviction. Claim-keyed flag counters are monotone: `claims_dropped` counts every distinct claim the flag has ever named (`_seenTotal`), independent of the rolling seen-window's evictions (w70-runtime F-3). A replanted retired claim is named by the echo flag and drained by value — it cannot re-fire while any consumption record stands. Schema-claim convictions are probe-verified at every layer: the marker consult catch, the transaction gate catch (`#schemaClaim`), and `store._schemaGuard` all prove the named table is actually gone before minting `Ledger schema diverged` — a foreign `RAISE` spelling 'no such table: X' over a healthy schema propagates as an engine fault, never divergence evidence; a probe that itself faults does NOT mint the conviction — it classifies `INV-503-LEDGER` (busy/locked) or `INV-503-STORAGE`, and an `unproven` verdict defers to the caller's own classifier instead of double-convicting (w72-seal F-2, w73-seal F-1/F-2). RELEASE is a latch-gated commit edge whose RETRY ORDER is the contract: a faulted `RELEASE` is followed by a `ROLLBACK TO` retry first — a release retried over a faulted rollback would COMMIT the span it meant to undo while `released` stayed false and the latches attested nothing — and only a proved rollback permits the release retry; an unresolvable release rolls the leaked transaction back and refuses `INV-503-LEDGER` (`INV-503-LEDGER` with 'caller transaction holds an unresolved savepoint' when the caller's own tx keeps it open), and the deferred latch is skipped on a faulted pass so suppression never mints over deletes that stood back up (w72-seal F-5, w73-runtime F-1). Every savepoint's `SAVEPOINT` statement sits outside its guarded try — a fault *establishing* the savepoint has no span to roll back or release, so the real error propagates instead of a phantom 'unresolved savepoint' (w73 self-audit). A `residue_note` write rolled back after its `RELEASE` faulted is flagged post-rollback as `floor_marker_retired_note_rolled_back` — the retiring set's carry note discarded while the mints proceed unsigned names itself rather than sealing silently (w73-fv F-3). The `marker_defeated` detail key is the re-latch contract: only INV-409s carrying it mint the defeat flag (a bare consult INV-409 cannot), and its `claims` field always names the full bound set — the flag slices its own 16-sample while `_seenTotal` counts every distinct claim ever named, so `claims_dropped` is monotone under re-latch and flood alike (w72-seal F-3/F-4, w72-runtime F-4). Consult faults are classified, never swallowed: `InvariantError` rethrows, schema claims probe-verify, errcode 5/6 rides `INV-503-LEDGER`, storage bases ride `INV-503-STORAGE`, and errcode-less throws propagate raw as eval faults (w72-seal F-1/F-6, w72-fv F-1). All three residue spans share one failure doctrine — a catch that cannot `ROLLBACK TO` sets `rollbackFailed` and the `finally` skips plain `RELEASE` (an unpaired release would COMMIT the span), recovery is ordered `ROLLBACK TO` → retry `RELEASE` → zombie reap (`!callerInTx && db.isTransaction` rolls the leaked transaction back and refuses `INV-503-LEDGER` 'leaked transaction rolled back') → dead-span rethrow (a `ROLLBACK`-class fault — a foreign `RAISE(ROLLBACK)` — destroys the savepoint's implicit transaction, so the arm discriminates `!db.isTransaction` / 'no such savepoint' and rethrows the REAL error instead of a phantom 'unresolved savepoint'), and the deferred-apply queue is deleted only when `released && spanError === undefined` so a faulted rollback can never commit the guard drops while reporting a storage fault (w74-runtime F-1/F-2, w74-seal F-1/F-2, w74-fv F-6). The integrity probes at store and target open run the same probe-verify doctrine — a schema-shaped probe fault (`no such table|no such column|not a database|malformed|has N columns but M values`) consults the column-bearing catalog probe before classifying, so a dropped-or-drained ledger table convicts `INV-409-INTEGRITY` at open instead of wearing `INV-503-STORAGE` 'Integrity probe fault' (w74-seal F-4); a probe fault riding a corruption-family errcode (base 11/26) convicts `INV-409` under `#schemaClaim` identically (w74-seal F-5). The schema probe is now type- and order-bearing everywhere it runs: a `sqlite_master` type check convicts a substituted VIEW, and `SELECT *` + `columns()` convicts a reordered same-arity table — positional inserts that would land swapped convict like a dropped table on store, target and the fabric consults (w75-fv F-6.1, w75-seal F-3, w75-runtime F-3); inside the store's schema-text branch the 1811/base-19 convictions fire BEFORE the probe-ok exculpation — a real trigger abort whose RAISE text happens to be schema-shaped stays `refused by a trigger` evidence instead of laundering out through the exculpation (w75-fv F-6.2), and insert-spelling schema claims convict on the target path identically (w75-fv F-6.4 + w75-seal F-2 + w75-runtime F-2). Engine-base faults (7/9/17) inside the retire and deferred-apply classifiers ride `INV-503-LEDGER` — a durable `marker_defeated` flag never convicts infrastructure (w75-seal F-5). A foreign `COMMIT` minted inside `SAVEPOINT deferred_mint` or `residue_note` convicts `marker_defeated` on the delivered result — `deferred_apply_error` carries the verdict rather than reporting a clean seal (w75-fv F-5.1/F-5.2); the residue-note span's retried `RELEASE` is silent so the zombie reap always reaches the rollback, and the dead-span rethrow surfaces `spanError` — the real evidence class — not the retry's noise (w75-seal F-1 + w75-runtime F-1); a release-faulted *successful* apply discloses 'deferred mint apply rolled back — the release fault discarded the span; queued claims retained for replay' so a silent discard can never masquerade as landed (w75-runtime F-4). The guarded schema surface is pinned between opens: `#schemaSurfaceAssert` fingerprints `PRAGMA schema_version` plus the trigger set once the ctor's shape probe has run, and every `_schemaGuard` re-verifies on version change — a live `RENAME`+`CREATE` column reorder, an attacker-added PRIMARY KEY, a dropped-CHECK rebuild, a substituted VIEW, or a TEMP shadow table/trigger on a ledger table convicts `INV-409` at the next guarded write instead of landing swapped-column garbage or orphaned guards (w76-fv F-1/F-2/F-3, w76-runtime F-1/F-1b); `LEDGER_SHAPE`/`TARGET_SHAPE` are one shared list per store so the probe and the pin cannot drift apart, and sanctioned drop+recreate runs inside `_ddlWindow` (`_ddlSanction` stands the assert down for its own span only). The store's `#ledgerSchemaProbe` now runs BEFORE the aad migration and the guard install — the convict verdict precedes the migration's own faults, so a substituted VIEW surfaces as tamper, not a generic 503 (w76-fv F-3). Savepoint failure doctrine tightened further: a zombie reap whose ROLLBACK faults names the refusal instead of claiming 'rolled back' (w76-seal F-2); a residue drain rolled back after its RELEASE faulted mints `floor_marker_retired_note_rolled_back` rather than sealing silently (w76-seal F-4); a foreign `COMMIT` inside the drain convicts on the attributed writes it lands mid-span, while a peer marker commit mid-kill reports defeat without minting a false conviction on our own bytes (w76-seal F-3a/F-3b); a classless consult fault propagates raw — never wrapped as an engine fault (w76-seal F-5a); the apply's `marker_defeated` flag requires `meta_kv` standing — a dropped ledger wears 'diverged' like its siblings (w76-seal F-5b); unhandled sqlite faults consult the probe so diverged schemas convict while standing schemas stay engine-class (w76-runtime F-2); and schema-shaped refusal text on a standing schema convicts refused-write while a schema probe that cannot answer classifies honestly instead of escaping raw (w76-seal F-1/F-1b).

**`facts_regressed` — folded rows rewritten mid-table.** The chain-facts memo fingerprints count/max-seq/tip-bytes; a mid-table envelope rewrite preserving all three keeps the stale (fail-closed) facts until an append moves the shape. On a re-derivation that yields FEWER deaths or revoked references than before — deaths are monotone under a live signer — the fold names `facts_regressed`: a folded row was rewritten into a non-matching envelope. This is conviction-adjacent evidence (the next full fold wedges the forged row anyway); treat it as an integrity incident and let the seal cut the tail.

**`AAD_MIGRATION` / `AAD_MIGRATION_MARKER` — pre-AAD residue attestation.** `meta_kv.aad_migration` rows are durable markers that a ciphertext migrated to tuple-AAD but crashed before attesting. Every open digests marker rows and re-attests what the chain lacks: a configured tenant lands `AAD_MIGRATION` with live counters and `marker_digests`; a row naming a tenant this deployment cannot sign for lands `AAD_MIGRATION_MARKER` under the first configured chain with `claimed_tenant` + `reason: 'unconfigured-tenant'`. Dedupe consults only *verified* signed migration rows whose PARSED envelope names the digest — an unsigned plant or a dup-keyed graft is evidence, never cover — and markers are deleted only once every digest has a verified anchor; with no signer to attest under they survive for a later configured open. The marker row itself is delete-guarded (`aad_marker_keep`) on both ledgers — an in-band delete aborts 'aad migration marker is evidence'; sanctioned post-attest cleanup drops and recreates the guard verbatim. A marker that re-appears after clearing means a writer planted it: the attestation is the trail. A dropped `meta_kv` self-heals empty at open — pending markers and `fold_floor` are destroyed while every read still succeeds — so an empty `meta_kv` under a non-empty `audit` is attested as `STORE_SCHEMA_RESIDUE` (`reason: 'meta_kv-empty-under-nonempty-audit'`) under each affected tenant's chain instead of being absorbed silently.

**`INV-409-INTEGRITY 'Ledger schema diverged'` — dropped or rewritten ledger tables.** Every audit surface (fold, bulk export, page/hash readers, key-death scans, record enumeration, `meta_kv`/`fold_floor` writes and the seal sweep) classifies raw sqlite schema failures (`no such table|no such column|not a database|malformed`) as `INV-409-INTEGRITY` rather than leaking `ERR_SQLITE` internals — a dropped `audit`/`grants`/`records`/`meta_kv` table is tamper evidence, not a crash to restart around. Restore from the last good backup; the surface that raised it names which reader convicted.

## Staging release and rollback

Verify archive checksums, the complete test suite and machine-readable release gate. Install to a new versioned directory, preserve the existing application version and data, and test against a restored synthetic copy before traffic changes. Do not run different incompatible binaries against live state. Current schema version is 1; the program refuses a newer schema. No destructive migration exists. Do not claim safe rollback across future migrations without an independently tested plan.

Before production change, establish the exact target, recovery owner and rollback method, then build, migrate non-destructively, restart only the assigned service, verify health/logs and run an authorised critical flow. Those live steps could not be executed without an assigned customer environment.
