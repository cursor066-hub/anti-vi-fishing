# Security model and review status

**Not independently assessed. Not approved for production.** Security-critical implementation was exercised by focused positive/negative tests, concurrency workers, fault injection, syntax checks, and a small source-pattern scan. These are evidence, not penetration testing, formal verification, ASVS certification, legal compliance or a complete vulnerability audit.

## Assets and adversaries

Assets are tenant action semantics, customer policy, signing authority, protected target state, evidence integrity, replay state and sensitive data. Caller sessions, inputs, network requests, proposed prose and evidence from communication channels are untrusted. The tested local profile assumes the customer host, runtime, local configuration, OS clock and registered public keys have not been compromised. Unlike the complete SRS threat model, it cannot withstand malicious OS memory access or compromise of the process holding execution/audit keys.

A valid session does not execute a protected mutation. Authority additionally requires typed action validation, independently signed scoped evidence, deterministic ALLOW, action-bound eligible signatures, and a short-lived registered single-use certificate. Tenant IDs are derived from authentication and checked again at cryptographic and storage boundaries. Encryption uses per-tenant keys with record-bound associated data. Revocation is monotonic and synchronous within the local state store; there is no remote propagation assurance.

## Implemented safeguards

HTTP uses exact host/origin matching, same-origin-only browser requests, HttpOnly SameSite=Strict sessions, CSRF tokens for cookie-based POSTs, request/header/body time and size limits, role checks, per-address/principal limits and safe generic unexpected-error responses. HTTPS terminates at an explicitly configured trusted staging reverse proxy; local HTTP is loopback-only. No CORS wildcards, browser persistent token storage, dynamic HTML injection, arbitrary SQL, external fetch endpoint, upload execution, hidden root bypass or public privileged default credentials are implemented.

The gate consumes authority before dispatch. Ambiguous target responses never become success and never trigger automatic mutating retries. Certificate registration equality prevents a caller from presenting a differently scoped envelope, even one signed by a local execution key outside the issuance path. It does not defend against full compromise of the trusted process or database/key host.

Software keys are generated using the platform CSPRNG and Ed25519 implementation inside the IF-SOFTHSM-1 vault: private material is AES-256-GCM-wrapped at rest under a separately stored master key, purpose-bound at use, and exports only when flagged exportable. Approval and genesis verification require distinct customer failure domains — **software multisignature, not threshold cryptography** at the approval layer; threshold (k-of-n Shamir) is implemented for secret recovery ceremonies with committed shares. Key rotation runs through a verified `key.rotate` action: the replacement is generated pending and cannot sign until activation; the retired key is recorded. Configuring `require_hardware` blocks all default software signers. No self-asserted API parameter can enroll a “hardware-backed” signer. `prepareRotation` accepts `suite` (Ed25519/ES256) so a rotation can migrate the signing algorithm. Recovery ceremonies honour `min_delay_ms` — reconstruction is rejected before the delay elapses — and every custodian gets a `RECOVERY_NOTICE_ISSUED` audit record at share-commit time (a stand-in for the physical OOB channel, which remains external). On configuration drift the gate withdraws transaction privileges (`INV-403-QUARANTINE`) until a security principal re-attests via `POST /v1/config-drift/reassert`. The `master.key` is a separate file in the same deployment directory as the vault — its filesystem separation from `vault.db` is real, but custody separation (different host, different principal, KMS/HSM custody) is a deployment concern this profile cannot enforce. Real HSM/MPC and certified ceremonies remain external.

### Secure Perception residual risks

Secure Perception raises the cost of extracting protected fields, it does not
prevent all visual exfiltration. Residual risks that remain even with a fully
attested hardware path:

- **External camera** — a phone can photograph the rendered screen.
- **Deliberate memorisation** — an authorised operator can memorise what they
  are shown; the module reduces bulk extraction, not human recall.
- **Compromised trusted hardware** — a compromised TEE/display-path component
  can render and leak plaintext despite valid attestation.
- **Side channels** — timing, pixel emissions and host-side channels are out of
  scope for the software profile.

Product copy and the console must never present the module as a trusted
display or as prevention of all visual exfiltration.

### Store plaintext surfaces (design decision)

The audit chain, `data_access` trail, `usage` keys, `nonces` and `idempotency` request hashes are stored **plaintext by design** inside `fabric.db`: audit envelopes must remain verifiable and servable to auditors who hold only public keys, and `verifyAudit`/export integrity checks are deliberately key-free. Confidentiality of the database file itself comes from the `0600` file permissions and the deployment's filesystem/backup controls — the tenant encryption keys (`config.json`) live in the same trust boundary, so encrypting audit metadata under them would not raise the bar against an attacker who can already read the directory. Integrity, however, is fully cryptographic: hash chaining, signed envelopes and per-row re-verification on read (`auditPage` recomputes digests and chain links before serving).

Residual honest limits:

- SQLite `secure_delete` cannot guarantee erasure of pages already flushed into filesystem snapshots or earlier backups — the retention report marks pre-erasure backup media as out of scope.
- A **file-level** `DELETE`/`UPDATE` bypassing the API leaves orphan wrapped DEKs (the key outliving its ciphertext) — a generic property, mitigated only by convention: all deletion goes through `remove`/`shred`, which destroy the DEK first.
- A WAL checkpoint is best-effort under writer contention; a busy checkpoint keeps the shred flag armed and retries on the next commit.
- **The store is trusted for tenancy but re-proven for integrity.** Rows write `tenant_id` as committed data; every read path that can mutate state re-verifies the record against the actor's own signed envelope (`request_intent` for capsules, the issuer envelope for evidence, the vault-signed envelope for outcomes) rather than trusting any stored digest column — an attacker who can `UPDATE` the file must also forge signatures, not just move digest fields in sync (w11-redteam).
- **Ledger reads are not audit-logged.** Reads of audit data (`auditPage`, `graph`, checkpoint serves) are intentionally unaudited — auditing reads of the audit log would be self-referential noise; the integrity of what a reader receives is cryptographic (digests recomputed on serve), not procedural.
- **Credential files are at-rest filesystem objects.** `config.json`, `master.key`, `vault.keys` and fixture private keys carry `0600` permissions and nothing else — there is no envelope encryption or OS keyring integration in this profile; process-level compromise of the deployment user reads them. Real custody (HSM/MPC/keyring) is on the external list.
- **Zeroization is best-effort over transient buffers.** Reconstructed secrets, share y-coordinates, deal-side plaintext/poly/coefficient buffers, ECDH shared secrets and derived AES session keys are `fill(0)`ed after use; what cannot be zeroed by design remains honestly heap-resident until GC — the vault master-key Buffer, per-tenant plaintext DEK maps (required for record decryption), per-decrypt plaintext `Buffer.concat` copies in `crypto.decrypt`, per-call `store.key()`/`dek()` derivation Buffers (returned keys cannot be zeroed before their caller uses them), and PEM/key strings the JS runtime interns at parse time (w11-timing MED-4, w15-timing F10 residual). Copies already made by the JIT are outside software reach — constant-time and zeroization claims in pure JS are engineering-honest, not proof-grade.
- **Perception ECDH residency is bounded, not instantaneous.** An expired session's `_server_private` is tombstoned by `retentionSweep` (security role, operator-invoked) — between session expiry and the next sweep the key sits decryptable at rest; the bound is policy `session_ttl_ms` plus sweep latency (w15-timing F2).
- **Issuerd work-path timing diverges on record presence.** A missing record answers after one digest while a hit runs the expect/extract loops before signing — both responses are identical signed envelopes, but server-side latency carries a weak record-existence signal (sub-µs → µs inside ~ms Ed25519 signing). Closing it fully means padding every miss to worst-case rule width — judged residual, honestly bounded (w15-timing F6).
- **Static source scans are a regex gate, not an AST gate.** `scripts/check.mjs` matches `eval(`, `Function(`, `Reflect.apply(eval`, `node:vm` and known credential shapes; indirection escapes it by construction (`globalThis['eval']`, `const e = globalThis.eval`, dynamic `import()` of a data: URL, `this.eval()` on a receiver). It is a tripwire for the obvious injection, not a proof there is no dynamic-code path — that class of assurance needs a real parser rule, not a pattern list (w11-supply SC-06).
- **Denial audits are sampled under pressure.** Pre-transaction `AUTHORIZATION_DENIED` ledger writes deduplicate identical (tenant, subject, code, message) denials for 60s — the ledger proves the denial happened and bounds ledger-growth/signing-CPU amplification from a low-privilege requester, but a sustained denial storm is recorded at reduced cardinality, not per request (w11-timing NEW-LOW-1).
- **In-process signer reach is the irreducible residual.** Authorization state is derived from the signed audit chain (`_auditIndex`), so a principal who can only edit store rows (UPDATE/DELETE/INSERT) gains nothing the chain does not attest — forged rows die at `verifySigned`/digest re-verification, deletions cannot un-anchor evidence, revocations, grants or data-access events. But a principal who can also *call* the vault signers (`signAudit`/`signExecution`) can mint legitimate-looking chain entries and rebuild the head; in-process tamper-resistance ends there by construction. This maps to BLOCKED_EXTERNAL custody (HSM/external witness) — no amount of in-process code closes it.
- **Trigger presence is checked, not proven.** `Store` verifies `no_audit_update`/`no_audit_delete`/`audit_seq_guard` exist at open and the seq-guard/RAISE path is exercised by tests; an attacker who drops the triggers AND rebuilds a consistent chain under the same audit key still defeats append-only enforcement — again bounded by the signer-reach residual above, not by SQLite triggers (w11-redteam R18).
- **Usage/rate/fanout accounting is chain-anchored; the `usage`/`idempotency` tables are mirrors.** Replay, per-second rate, rolling budgets and the fan-out set are computed from signed `RUNTIME_ALLOWED`/`RUNTIME_DENIED` chain events (`_auditIndex.runtimeUse`), not the mutable rows — a store-level principal who inserts or deletes usage rows can neither refill a budget nor replay a request (w13-fixverify M1/M5). Residual: a forged `usage` row can still collide on the table's PRIMARY KEY and turn a matching consume into a fail-closed `INV-503-GATE` — availability only, never a flipped verdict.
- **Anchoring begins where the chain begins.** A pre-upgrade ledger segment (nonces minted before the perception namespacing, disclosures before `DATA_ACCESSED` events, sims before `POLICY_SIMULATED` digests) is honoured through explicit legacy paths — legacy nonce rows still block replay, legacy grants resolve through their issuing capsule's digest — but history older than the first signed event cannot be cross-proven; a database snapshot from before the upgrade boundary replays as legitimate history (w13-fixverify L9).
- **A whole-database rollback is a restore, not a tamper.** Restoring a byte-identical older `fabric.db` (or replaying one after `VACUUM`) rewinds every anchored projection consistently — consumed nonces, revocations, grants re-become un-consumed/un-issued exactly as at that snapshot's time. The honest boundary: an externally witnessed checkpoint (audit export pinned off-host) detects the rollback; without a pinned head, a consistent older snapshot is indistinguishable from the present — documented under AUD-008's witness model (w13-fixverify F12).
- **Fresh-open tail amputation needs a witness.** Deleting the newest audit tail (events + their records) before first reopen — while the chain head was never pinned outside — leaves a shorter, self-consistent chain. The trigger/seq-guard layer blocks *interior* edits, and `auditConsistency` + externally pinned checkpoints detect the amputation at compare time; nothing inside the database can detect a truncation of a head nobody witnessed (w13-store F6).
- **The export itself is a re-verification pass, and `prior_checkpoint` is the witness chain.** `auditExport` recomputes every row's digest, sequence, `previous` link and signature before the checkpoint signs the head — a tampered-but-parseable row cannot fold into a signed checkpoint (it aborts the export with `INV-409-AUDIT-TAMPER`). Each bundle carries the previous export's signed checkpoint, so amputating or rewriting a suffix *after* an export breaks verification instead of self-certifying — provided at least one checkpoint is pinned off-host (w16-fixverify F11).
- **Bogus wrapped key material is a liveness hazard, not an authority hazard.** A store-level plant can seed `vault.keys` entries whose `wrapped` blobs unwrap to garbage — signing under them fails at use time (`SignJWT` throws), never silently mints. Reopen attestation (`generated_inside`, `attested_at`, purpose/key-class consistency) rejects foreign entries from trust; the residual is a rotation ceremony mid-flight wedge requiring operator `reanchor`-style repair, not a forged signature path (w13-store F13).
- **Tenant config is frozen at open, not at edit time.** `config.tenants` (identities, issuers, keys, components, policy genesis) is deep-frozen after construction — a post-open in-process edit throws `TypeError` rather than silently shifting trust anchors; a file-level rewrite between opens is caught by the persisted config snapshot (`_configDrift`). Boot-time tampering before the freeze is the same signer/file-co-location boundary as `master.key`.
- **Anchored lifecycle verdicts are fail-closed by construction.** Ceremony lifecycle (committed/completed/aborted/notice-coverage/rotation-spend), the clock-recovery veto enumeration and the staged-policy anchor all read from the signed fold, not from mutable rows — so a store-level attacker who edits or deletes a ceremony/policy/certificate row can only *kill* the object (quorum dies, promotion retires the row, recovery vetoes on missing anchored rows), never resurrect or redirect it. The honest cost: a targeted row delete or status flip is a per-object availability denial — the operator repair is `sealAuditChain`/`reanchorPolicy`, and a poisoned audit tail wedges only its own tenant until sealed (`_clockRecoveryUnverifiable`) instead of halting recovery for all (w18-fixverify F5/F6/F12).
- **Denial-dedup collapses by (tenant, subject, code) inside a 60 s window.** `_containMemo` and the rejection-audit memo share one signed ledger row per identical denial tuple — the verdict is always recorded at least once, but two *distinct* denials carrying the same code for the same subject inside the window merge into one record. Availability and correctness of each live response are unaffected; the granularity loss is an evidence-volume tradeoff, and the window is consumed only after the guarded write lands (a failed write never suppresses the real event) (w18-fixverify F4).
- **Perception component ECDH keys are static per deployment.** Sealed releases derive their session cipher from the component's long-term ECDH key (`component_ecdh` on the attested session); a later component-key compromise exposes the ciphertext of earlier sealed envelopes — no forward secrecy. Ephemeral-per-session component keys with rotation windows are the correct upgrade and sit with the hardware attestation milestone (w18-issuerd F-17 residual).
- **Vault/data-key ciphertexts keep slash-form AAD pairs internally.** The tuple-AAD migration covered every table whose ciphertexts are addressed by (`kind`,`id`); `vault.keys` wrapped material and the data-key envelope bind by (`purpose`,`key_id`) pairs that are themselves consistent — the format is a cosmetic legacy, not a loosening; both remain undecryptable under any other pair (w19-aad W19-5).
- **A donor-deleted move transplant is undetectable at the receiver.** The AAD migration dedup window (`aadDedup`) catches a ciphertext grafted while the donor copy still exists — but a graft whose donor row was *deleted first* leaves no collision to observe: the planted ciphertext is AAD-consistent in its new home. Mitigation is procedural (donor stores are sealed before disposal; `auditExport` witnesses the deletion) — a cross-store cryptographic lineage would need external witnessing, same boundary as whole-database rollback (w19-aad move-transplant residual).
- **AAD migration quarantines both copies on collision — fail-closed, honestly DoS-shaped.** When `_migrateAad` sees the same ciphertext under two identities (slash-name, alias, `…/dek` tail, cross-database graft), BOTH rows are quarantined/sealed rather than one laundered through: a transplant can never pick a readable identity, at the honest cost that a determined attacker can also wedge a victim's honest rows. The per-tenant `aadMigration` stats map (`migrated`/`transplants`/`ambiguous`/`skipped`) surfaces exactly what was quarantined so the denial is visible, never silent (w19-aad design).
- **Clock recovery veto is per-tenant; a genuinely resurrectable authority still vetoes globally.** Integrity failures inside one tenant's fold (missing, divergent or unverifiable anchored rows) isolate that tenant as `unverifiable` while others transact — but an *intact* anchored certificate or capsule whose expiry honestly lands inside the rewound span still refuses recovery for everyone (`INV-503-TIME`), because resurrecting lapsed authority is a veto, not a tamper signal (w9-network F4 / w19-lifecycle F3 boundary).

### Data gate design limits (w6-tenancy audit)

- **Ceremony endpoints are the governance path themselves.** `createCeremony`/`acknowledgeCeremony`/`commitCeremonyShares`/`reconstructCeremony` do not take capsule approvals or evidence envelopes — the custodian acknowledgement quorum IS the consensus (distinct failure domains, current-artifact consent, live custodian identities, ceremony-bound devices, recovery-delay floor from the `key.ceremony` rule's `cooldown_ms`). The rule's `approval_threshold`/`evidence_kinds` clauses govern `key.ceremony` ACTION capsules (the capsule authorization path), not the ceremony protocol endpoints (w6-ceremony F8).
- **Retention erasure is evidence-scoped by design.** `retentionSweep` shreds `evidence` records (and any undecryptable residue) only; `capsule`, `certificate`, `outcome`, `revocation`, `ceremony`, `jit-grant`, `policy-history`, `evidence-tombstone`, `nonces`, `usage`, `data_access` and `idempotency` rows persist for the life of the ledger — they are the authority record the audit chain and idempotency guarantees depend on, and expiring them would be silent history loss. Kind-scoped retention beyond evidence is a policy extension, not implemented in this profile (w7-dek F7).

- **Capsule snapshots are stored plaintext.** A capsule's `current_state.material_fields` holds the dataset rows it was proposed against — required so the governed path can pin and later re-verify the exact snapshot. Rows are redacted from every read surface (`capsuleView` serves `{row_count, rows_digest}` on the record and inside the served `request_intent`/`requested_state` projections; certificate `constraints.current_state` carries `{version, digest, material_fields_digest}`), so an approver sees digests, not data they were never granted. Signed envelopes served to readers are therefore projections: the signature was verified at attach/mint time and cannot be re-verified byte-for-byte against the redacted copy. The stored plaintext sits in the same `fabric.db` trust boundary as the audit chain above.
- **Stored outcomes never re-serve exported rows.** `GET /gate/v1/outcomes/{id}` and `POST .../outcomes/{id}` (reconcile) return the signed outcome with `payload.output` projected to `{row_count, rows_digest, redacted: true}` — the row delivery happens once, inside the `execute()` response to the certificate bearer. A second subject cannot drain another subject's export history from the outcome store without a `data_access` charge; forensic readers keep the digest and watermarks. The target journal likewise persists an export's `observed_state` as `null` (digest-only): the whole-dataset snapshot — which includes columns the requester may not see — is never written to the durable journal (w10-datagate F5).
- **The proposer is trusted with the snapshot.** A `data.export` capsule's `current_state.material_fields` pins the dataset rows it was proposed against, so the proposer necessarily already holds those rows. The gate does not defend against a proposer proposing exports of data it already possesses — it guarantees the authorised egress (approved columns/rows, transforms, watermarks, coverage accounting) is the only form that leaves under a certificate (w10-datagate F11).
- **`MONITORED` coverage is self-attested by the data gate.** A manifest's `MONITORED`/`UNKNOWN`/`UNCOVERED` labels and their freshness are evaluated and served by the same software that enforces the gate — there is no independent monitor, drift agent or external attestation proving a path really is observed. The honest reading of `MONITORED` is "the gate was told this path is watched"; it is not third-party evidence (w11-ledger F11/F12).
- **Key revocation is real, and revoking the audit key wedges signing.** `revoke('key')` now binds the signing paths (`signExecution`, `signAudit`) and the pending-key activation gate — the ledger record, not the vault flag, is authoritative. Consequence: with the tenant's audit key revoked, no outcome/revocation/coverage/checkpoint envelope can be signed until a certified `key.rotate` activates a successor; operators must rotate a compromised audit key rather than revoke it outright. Revoked keys still verify their historical signatures (revocation is not retroactive erasure).
- **Denied gate attempts record nothing.** The reconstruction check computes coverage prospectively and writes touch rows only when the gate allows — identical to the consume path's rollback semantics. A denied probe therefore does not burn budget (no self-DoS ratchet), but it also means coverage probing is free: the denial response itself reveals prospective `row_count`/`column_count`/`coverage_percent`, which is accepted oracle surface documented here.
- **Freshness binding covers every action class.** `assertFreshSnapshot` binds secret.use capsules to the secrets-registry row and every other action to the resources row; untracked ids synthesize an empty state so a fabricated snapshot fails the comparison instead of skipping the check.
- **Watermarks are forensic, not robust.** The attribution watermark is separable HMAC metadata bound to the exported field set — an attacker who can mutate exported fields strips it; any mutation also invalidates attribution. It deters and attributes leaks, it cannot prevent copying.
- **Reconstruction budget is per-subject AND dataset-wide.** The per-`(tenant, subject, dataset)` cap applies as before; a second cap (`max_dataset_coverage_percent`, defaulting to the subject coverage cap) bounds the UNION of every subject's touches on the dataset inside the window — a fresh identity minted by `jit.grant` cannot double a dataset's total disclosure (w10-datagate F2). Colluding subjects can still spend independent budgets across *different* datasets; cross-dataset correlation is an SIEM/witness-layer concern.
- **Process-global objects carry tenant attribution, not isolation.** The `KeyVault` and the monotone clock row are process-global; vault entries now carry `tenant_id` and every consumer (rotate/revoke/list/attest) enforces ownership, but in-process memory disclosure between tenants is out of scope — tenant separation is at the store/envelope layer, not the heap.
- **Process-wide metrics exist but are not served.** `/v1/metrics` returns only the caller's tenant slice; unattributed requests (no resolvable principal) are counted process-wide and never attributed to a tenant.
- **The SQL layer trusts its callers.** `readDataset`/`executePlan` re-verify the caller's own plan arguments rather than enforcing columns/row_ids at the query layer — safe today because every caller pre-validates through the gate, but any future direct consumer must enforce grants itself; the invariant is documented at the call site and in `docs/ARCHITECTURE.md`.
- **The ceremony dealer holds all shares transiently.** `splitCeremonySecret`/`commitCeremonyShares` generate the full Shamir share set inside one process before shares are handed to custodians — the dealing principal (a `security` officer or a member custodian) necessarily sees every share in memory during the ceremony. That is a sole-custody moment inside the software profile: a dealerless/MPC DKG would remove it, and is on the external list alongside real HSM custody. The ledger records `CEREMONY_PLANNED`/`SHARES_COMMITTED` so the dealing event is attributable, and committed-share digests let every custodian verify their share wasn't swapped post-deal.
- **Merkle proofs prove inclusion, not content authenticity.** `GET /v1/audit/proofs/{sequence}` and `/consistency` prove a row sits in the append-only tree at a given size — they do NOT re-prove the row's envelope signature or semantics. A verifier must check the signature over the proven leaf independently; the proofs bound *where* a row lives, not *what* it says (w13-supply W13-03).
- **Audit-key revocation kills post-revocation signing, not its history.** The signing window (`keyDeadAt` in the index projection) rejects rows minted by a key after the sequence of its `AUTHORITY_REVOKED`/`KEY_ROTATED` death row — inclusive boundary, so the death row may be self-signed. Rows legitimately signed by the pending successor after the death event verify normally; recovering from a leaked audit key is `key.rotate` + `revoke`, never `revoke` alone (w13-supply W13-01).
- **`check.mjs` is a lint-tier heuristic, not a security gate.** Its static scans are regex/text checks that catch honest regressions (missing call sites, stale docs, traceability gaps); they are not a proof of correctness and can be spoofed by a motivated committer. The actual security posture lives in the runtime invariants and the test suite; treat check results as CI hygiene signal only (w13-supply W12-06).
- **A forward clock excursion cuts honest rows too.** The monotone floor writes rows at `max(now, prior_time)` — if the host clock jumps forward and later returns to real time, those honestly-signed future-time rows violate the fold's acceptance bound (`pl.time <= max(consumeNow, prevPlTime) + 60s`) and wedge the index on every reopen. The designed repair is `sealAuditChain` (amputates the inflated tail it now sees) plus `recoverClock` (records the discontinuity on-chain): forward excursions cost the tail rows between the excursion and the regression — honest history sacrificed rather than hidden (w17-redteam E1, w17-idx F4).
- **Clock recovery is process-wide and veto-able by any honest tenant.** `recoverClock` rewinds one shared monotone clock; an intact live certificate in ANY tenant whose expiry lands inside the rewind window vetoes the recovery (`INV-503-TIME`) — a wedge that needs every in-flight certificate to expire or be revoked before the operator repair proceeds. Tamper evidence no longer vetoes globally: a tenant whose anchored rows are missing or divergent is isolated as `unverifiable` while the rest transact, and it rejoins only after `sealAuditChain` (w17-redteam D2, w19-lifecycle F3).
- **A failed fold forces one rebuild per request, bounded.** `_auditIndex` evicts its projection on a thrown fold (a poisoned row wedges consistently, never flaps) — but a caller who can keep supplying the poison trigger re-pays one chain rescan per request until an operator seals or removes the poison. Bounded by the same-origin authorization requirement and the wedge semantics; the index cannot be made to cache "bad" (w17-idx F5 residual).
- **Legacy grants die with their issuing capsule row.** Pre-upgrade JIT grants (issued before `scope_digest` anchoring) resolve their anchor through the issuing capsule's request digest — deleting that capsule row silently retires the grant's scope: availability loss only, never scope expansion; grants anchored by `scope_digest` are unaffected (w17-fixverify L2).
- **Session cookies bind the host, not the port.** The console session cookie is `HttpOnly`/`SameSite=Strict` but carries no port scope — any second process bound to a different port of the same host shares cookie reachability. Dev/staging consoles on a shared host must run on distinct hostnames; single-origin production deployment is the assumed posture (w17-console F6).

- **Release verification is only as strong as the pinned anchor.** `scripts/verify-release.mjs` is self-contained (it executes no artifact code) but the trust anchors MUST be supplied out-of-band — an anchors file inside the artifact certifies nothing and is refused unless `--anchors-in-tree` is passed for the CI fixture roundtrip. Consumers should also pin the verifier script itself. Production release signing does not live in this pipeline: `release-sign` must run in a protected CI `environment:` job holding the real release key so `--require-ci` attestations can truthfully bind a run (w15-supply F-2/F-10).
- **Manifest hashing binds content bytes, not file modes or line endings.** `MANIFEST.sha256` covers `sha256(content)` only — exec bits and permissions are not hashed (fail-open on metadata), and verification is defined on LF checkout semantics (`core.autocrlf=false`/Linux-x64); a CRLF checkout reports mass `tampered:` (fail-closed, but platform-fragile) (w15-supply F-12).

## Reporting and release ownership

No operational security-reporting inbox, legal entity, incident team, signer identity or external assessor was provisioned. This is a public-release blocker, not a fictitious security contact. Deployment owners must establish a monitored private reporting channel, acknowledgement/escalation policy and update process before any public beta. Do not send real vulnerabilities or customer data to an unverified address from a draft document.

Do not commit local `var/`, `.env`, database files, access tokens, software private keys or backup material. The distribution contains public synthetic audit examples only. `reports/sbom.cdx.json` inventories the application and tested runtime; it does not replace a transitive runtime/container SBOM or current advisory scan.
