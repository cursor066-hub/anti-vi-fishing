# Operator and customer workflows

## First finance transaction

Run local bootstrap and start the server as described in the README. Sign in as the operator. Under Propose action, choose `finance.beneficiary.create`, choose a new target resource identifier, and read its empty current state. Enter the synthetic vendor identifier, exact bank account, currency, purpose, validity and compensation procedure. Nothing is prefilled for an intentional financial value.

Open the resulting action and copy its capsule digest. Evidence must be generated by an independently controlled, configured issuer key. The package’s `scripts/simulate.mjs` and `tests/helpers.mjs` demonstrate the complete **synthetic** issuer process. The service does not let an operator declare an unsigned bank proof authoritative. The payload has these mandatory fields:

```json
{
  "evidence_id": "issuer-assigned-unique-id",
  "tenant_id": "acme",
  "capsule_digest": "the-actual-64-character-capsule-digest",
  "kind": "ownership",
  "content_digest": "the-actual-64-character-source-content-digest",
  "acquired_at": 1788648000000,
  "expires_at": 1788648600000,
  "confidence": 100,
  "advisory": false,
  "claim": "supports",
  "dependencies": [],
  "provenance": "Issuer verification method and transformation description",
  "retention_until": 1788649200000
}
```

The shown timestamps and explanatory digest strings are **documentation only**, not valid fresh evidence or ready-to-submit authority. Use actual current values and computed digests. Sign with `node src/cli.mjs sign --purpose evidence --key YOUR_ISSUER_KEY --input YOUR_PAYLOAD --output YOUR_ENVELOPE`. The CLI refuses to overwrite output files. Attach the resulting envelope in the evidence form. Add eligible independent evidence; correlated/dependent sources do not count as separate domains.

Sign out and sign in as an eligible custodian/approver. Review the amount, destination, current/requested fields, purpose, expiry and capsule digest. Download the exact approval challenge and sign offline:

```sh
node src/cli.mjs sign --key ./var/local/offline-custodians/acme-custodian-1.json --input ./approval-challenge.json --output ./approval-envelope.json --purpose action-approval
```

Submit the signed envelope while authenticated as the same signer. Repeat with a different eligible independent signer. These example key locations are solely for the local software evaluation. Sharing all keys on one host does not establish independent physical custody. Adding evidence changes the evidence graph and invalidates prior approvals.

Return as operator. Evaluate; the action reaches ALLOW only if every predicate holds. Mint its short-lived, single-use certificate. Dry-run leaves both the target and certificate unconsumed. Execute changes the isolated target only. The observed result is signed. Repeated execution is rejected; use reconciliation to inspect an uncertain outcome.

For a first-payment simulation, use `beneficiary-1` with the seeded synthetic bank account and currency. `quantity` equals `amount_minor`; the destination equals the bank account. A changed beneficiary or already-completed first payment fails the target predicate. A bank-detail change has proposal cooldown plus a target first-payment eligibility delay.

## Policy governance

A policy administrator loads the active constitution, edits a candidate, and runs the exact diff simulation. Simulation never activates policy. It is a current-time what-if evaluation of up to 500 recent stored actions, not a forensic replay at each historical timestamp. Candidate and baseline digests are persisted.

Activation requires a `policy.change` capsule through the API, exact candidate/baseline simulation, next sequential version, governance evidence, a mandatory delay, and three independent customer custodian software signatures. An ordinary policy-administrator token cannot activate policy. There is no unprotected rollback; a rollback would be a newly reviewed next-version policy and cannot clear the monotonic revocation store.

## Runtime access

The console’s runtime form creates an exact capability for the synthetic `dataset-1` resource, approved `customer-vault` destination and configured operations context. Enter explicit rows, columns and volume. Each actual read consumes shared information units; changing token IDs cannot reset the rolling budget. Forbidden columns, wrong destination/device, expired health, token replay, excessive rate, quarantine and changed policy fail closed.

Service-connect capabilities similarly validate a local software envelope. They do not create network sessions or prevent real packets. See the requirement matrix for the unimplemented endpoint/network enforcement layer.

## Audit and retention

An auditor or security operator exports the metadata log with an explicit purpose; access is appended to the log. Independently obtain and pin `trust-public-acme.json` from local bootstrap. Verify the export with `scripts/verify-export.mjs` or the independent WebCrypto implementation. Never establish customer trust solely from the public key included in an untrusted export. A prior independently held checkpoint adds prefix/fork detection. The sample pinned key in this ZIP authenticates synthetic sample evidence only.

Security operators can apply evidence legal holds and run the logical retention sweep. Evidence referenced by nonterminal actions is held; legal hold always wins. Eligible expired evidence is replaced by a digest-only tombstone, and per-record DEK crypto-shredding destroys the record's data-encryption key (`secure_delete=ON` zeroes freed pages; the WAL is truncated post-commit). The honest residual: ciphertext written into backups taken **before** erasure survives, so complete erasure of pre-erasure backups is **not** claimed.

## Platform workflows (v2)

### Live evidence acquisition

With `issuerd` running (`node src/cli.mjs issuerd --dir <deploy>/issuers`), `POST /v1/action-capsules/{id}/acquire-evidence` with `{issuer, kind, claims}` fetches a fresh signed envelope and attaches it in one audited transaction. `issuer` is the registered issuer name, `kind` one of its declared evidence kinds, `claims` the query fields (e.g. `{account, owner_id}` for `bank.ownership`). A `conflict` claim or missing record is escrow, never silently supports.

### Key rotation ceremony

See RUNBOOKS → rotation procedure. The pending replacement key is listed under Key vault with status `pending` until a verified `key.rotate` action activates it; `Attest` downloads its signed software attestation.

### Threshold secret recovery

Create a ceremony with custodian subject ids and threshold k (Ceremonies view or API). Custodians acknowledge offline; then the operator pastes the base64url secret and receives k-of-n committed shares for distribution. Reconstruction needs k distinct shares — a duplicated share does not extend quorum, and the service never stores the reconstructed secret.

### Staged policy deployment

A `policy.change` proposal whose `next.not_before` lies in the future passes the same governance (simulation, evidence, custodian quorum, cooldown) but is stored as `staged` rather than activated. `GET /v1/policy/history` exposes it; `activateDuePolicies` promotes it exactly one version at `activate_at`. A staged policy that would skip a version is refused, not queued.

### Emergency policy

An emergency policy names `emergency_of` equal to the active version, expires within `emergency_max_ttl_ms`, and must tighten **every** rule's approval threshold by at least `emergency_extra_custodians`. A candidate that loosens any rule is denied with `EMERGENCY_WEAKER`; approval requires the extra custodian signature.

### Composite actions

`action.composite` binds up to 16 certified, unconsumed children of the same actor — each child's semantic binding is preserved individually, no silent scope merge. A child failure triggers `target.compensate` on the already-applied children and lands COMPENSATED.

### Secure Perception (dev-attested)

Sign an attestation with the dev component bundle (`component-<tenant>.json`) offline, then `POST /v1/secure-perception/sessions`. `release` returns fields sealed to the session's ECDH channel — the browser cannot read them without the session key. `fallback` records a controlled-workspace decision with its reason. The session is honest software attestation: never a trusted display.

### Audit proofs

`GET /v1/audit/proofs/{seq}` returns the RFC 6962 inclusion path for an audit entry plus the current tree head; `GET /v1/audit/consistency?first=N` proves append-only history between two tree sizes; `POST /v1/audit/verify-proof` verifies a fetched proof server-side.

### JIT grants

A verified `identity.jit.grant` action mints a time-bound grant listing in `GET /v1/grants`; runtime capability issuance merges active grants into the caller's entitlement check. Expired and revoked grants drop out automatically.
